# 第二章 相关工作

本章围绕本文研究所涉及的关键方向进行综述。本文基于 MMQA（Multi-Table Multi-Hop Question Answering）复杂多表评测基准开展研究，该任务处于自然语言处理、信息检索和数据库系统的交叉领域。本章将依次介绍单表问答与 Text-to-SQL 技术、面向表格推理的大语言模型、多表评测基准，以及多表检索与 Text-to-SQL 评估方法，为后文的系统设计奠定理论基础。

## 2.1 单表问答与 Text-to-SQL 相关研究

表格问答（Table Question Answering, Table QA）旨在根据用户提出的自然语言问题，从给定表格中检索或推理出答案。早期研究主要面向单表场景，典型数据集包括 WikiTableQuestions、WikiSQL、SQA、FeTaQA 等。这类任务通常要求模型理解问题中的实体、属性、过滤条件和聚合意图，并在单张表格中定位答案单元格或生成相应查询语句。由于输入表格规模相对有限，模型主要关注问题与表格列名、单元格内容之间的语义匹配。

早期单表问答方法通常依赖规则模板、语义解析或浅层特征匹配，将自然语言问题映射为一系列表格操作，例如选择、过滤、排序、计数和聚合。此类方法具有一定可解释性，但对人工规则依赖较强，难以覆盖复杂多样的自然语言表达。随着深度学习的发展，研究者开始使用神经网络对问题文本和表格结构进行联合表示，通过注意力机制学习问题词与表格字段之间的对应关系，从而提升模型对同义表达、隐式约束和复杂条件的处理能力。

Text-to-SQL 是表格问答中的重要方向，其目标是将自然语言问题自动转换为 SQL 查询语句。与直接输出答案的表格问答不同，Text-to-SQL 更关注模型能否根据自然语言问题和数据库 Schema 生成结构化查询逻辑，包括选择字段、筛选条件、聚合函数、排序方式以及表连接关系等。Spider、BIRD、SPINACH 等数据集推动了复杂 Text-to-SQL 任务的发展，尤其是 Spider 数据集涵盖多个领域的多表数据库，要求模型具备跨数据库泛化能力。

需要说明的是，本文的研究重点并不是提出新的 Text-to-SQL 方法，MMQA 原论文也主要将 Text-to-SQL 作为评估大语言模型能力的子任务之一，而不是围绕 SQL 生成方法本身展开专门研究。本文同样将 Text-to-SQL 作为补充实验，用于观察当前大语言模型在给定正确表结构条件下的 SQL 生成能力。本文的主线仍然是多表检索，即如何从全局表池中筛选出支撑后续推理的关键表结构。Text-to-SQL 链路在本文中主要用于辅助分析：当检索噪声被标准表头屏蔽后，大语言模型是否仍能生成形式上接近标准答案的跨表 SQL。

## 2.2 面向表格推理的大语言模型

大语言模型（LLMs）凭借海量语料预训练，在代码生成与逻辑推理上展现出巨大潜力。现有研究通过指令微调或思维链（CoT）提示，使 LLMs 能够处理表格-文本混合问答或离散数值推理。此外，TableLLM、TableLlama 等垂直领域模型通过在表格数据上的继续预训练，增强了对表格 Schema 及单元格关系的理解，说明大语言模型具有处理结构化数据的潜力。

然而，现有方法多局限于单表场景。在真实的多表多跳任务中，模型不仅需要理解单表列名语义，更需识别跨表的主外键、共享列及桥接关系，并规划多步推理路径。这对大语言模型的长上下文处理能力与图结构理解能力提出了极为严苛的挑战。

## 2.3 多表任务与 MMQA 评测基准

现实数据库通常由多张表构成，不同表之间通过主键、外键或桥接表形成复杂关系。因此，多表任务比单表任务更接近真实应用场景。多表任务通常要求模型在多个表中定位相关信息，并根据表间连接关系完成推理或生成查询。已有研究中，多表任务包括从多表中生成子表、基于文档和多表内容进行摘要、跨表检索以及多表数据库上的 Text-to-SQL 等。

已有多表研究为复杂表格理解提供了基础，但仍存在一定不足。一些方法关注子表生成或粗粒度表格选择，主要考察模型能否从多个表格中找出相关区域；一些方法考虑多表数据库中的 SQL 生成，但更关注最终 SQL 的正确性，而没有系统分析表检索、键选择和多跳推理等中间能力。对于大语言模型而言，如果只观察最终问答或 SQL 执行结果，很难判断错误来自表检索、键关系识别、推理顺序判断还是 SQL 生成阶段。

MMQA（Multi-Table Multi-Hop Question Answering）基准正是为了评估大语言模型在多表理解和推理任务中的能力而提出。与传统单表基准不同，MMQA 强调“多表”与“多跳”特征，要求模型利用主外键约束完成跨表证据收集与推理。该基准提供了一套包含多表检索、Text-to-SQL 生成、多表问答及键选择任务的综合评估框架。本文项目正是基于 MMQA 的任务设定展开，重点关注其中的多表检索链路，并将 Text-to-SQL 作为补充评估任务，用于考察大语言模型在给定正确表结构时的 SQL 生成能力。

## 2.4 多表检索与问题分解方法

多表检索（Multi-Table Retrieval, MTR）是 MMQA 中的重要任务。给定一个自然语言问题和一个全局表池，系统需要检索出回答问题所需的一组表。与单表检索不同，多表检索不仅要求找到与问题语义直接相关的表，还需要找到与已检索表存在结构关联的桥接表或中间表。例如，一个问题可能直接提到“负责人”和“部门”，但生成正确查询还需要连接“管理”表；该桥接表可能没有明显出现在问题字面中，却是跨表推理的关键。

传统文本检索方法主要依赖问题和候选文档之间的语义相似度。在表格场景中，常见做法是将表名、列名和部分单元格内容序列化为文本，再使用 BM25、预训练语言模型或密集向量模型计算问题与表之间的相似度。语义检索方法实现简单、计算效率较高，但容易受到通用列名和表名歧义的影响。例如，不同表中经常出现 id、name、date 等通用字段，仅依靠语义相似度难以判断其真实作用。

为了解决纯语义检索难以召回桥接表的问题，MMQA 提出了基于问题分解的 MTR 算法思想。该方法利用大语言模型将复杂的长难句拆解为有序的子问题序列，进而将多表检索转化为多轮迭代的单表检索。在迭代过程中，系统综合考量“子问题-表”的语义相关性与“表-表”的拓扑连通性，逐步发现隐蔽的桥接表。

表间相关性建模是多表检索中的一关键问题。MMQA 原论文中主要根据表格列交集判断表间相关性，即若两个表存在共享列，则认为它们存在一定连接关系。该做法简单直接，但在实际工程中可能存在两类问题：一方面，列名相同不一定代表真实连接关系；另一方面，真实主外键关系有时并不表现为完全相同的列名。本文在实现过程中结合主外键关系、共享列和结构相似性等信息构造表间关系得分，并在实验中比较不同传播策略对检索结果的影响。

由于 MMQA 原论文未公开完整源码，且部分算法细节描述较为抽象，本文没有简单照搬论文伪代码，而是在复现基础上进一步进行了工程化改进。在“子问题-表”的语义相关性计算方面，原论文采用单表检索模型为候选表打分；本文结合本地实验环境和运行效率需求，将候选表 Schema 与问题编码为向量表示，并使用向量点积计算语义相似度，从而实现更轻量的全局表池扫描。与此同时，本文引入最大连通性截断、残差平滑、不确定性门控和局部候选池重排等策略，以缓解全局传播中的噪声累积问题。这些改进构成了本文第三章多表检索模块设计的基础。

## 2.5 多表检索和 Text-to-SQL 的评价指标

本文的实验评估主要分为两部分：一是多表检索能力评估，二是 Text-to-SQL 生成能力评估。前者用于分析系统能否从全局表池中召回支撑多跳推理的关键表，后者用于分析在已知正确表结构条件下，大语言模型能否生成形式上接近标准答案的跨表 SQL。由于两类任务的目标不同，本文分别采用不同的评价指标体系。

（1）多表检索评估

多表检索任务通常采用信息检索领域的评价指标。Recall 用于衡量标准相关表中有多少被成功召回，是多表检索中最重要的指标之一；Precision 用于衡量检索结果中有多少是真正相关表；F1 综合考虑 Precision 和 Recall，用于反映检索结果的整体平衡性；MRR（Mean Reciprocal Rank）关注第一个相关结果在排序中的位置，用于反映排序前列质量；MAP（Mean Average Precision）则综合考察多个相关表在排序列表中的整体排序情况。

对于 MMQA 这类多表任务而言，仅关注 Top-1 结果并不充分，因为回答问题往往需要多张表同时被召回，且桥接表或中间表的排序位置也会直接影响后续链路的可用性。因此，本文在不同的 Top-K 设置下综合使用 Recall、Precision、F1、MRR 和 MAP 等指标，对纯语义检索、问题分解、paper-like 传播、改进版 E1、E2_HYBRID 和 E2_HYBRID_LOCAL 等多种检索策略进行系统比较。

（2）Text-to-SQL 评估

原论文对 Text-to-SQL 的评估主要采用 ROUGE 和 BLEU 等文本相似性指标，即比较模型生成 SQL 与标准 SQL 在文本层面的接近程度，而没有进一步验证 SQL 是否能够在数据库中正确执行。本文保留这一评估思路，将 Text-to-SQL 作为补充实验，主要用于测试不同大语言模型在统一输入条件下的 SQL 生成能力，而不是将其作为本文的核心算法贡献。

具体而言，本文对 Text-to-SQL 结果主要采用三类指标进行比较。其一，ROUGE-1 用于衡量生成 SQL 与标准 SQL 在词级别上的重合程度。其二，ROUGE-L 关注最长公共子序列，能够在一定程度上反映生成 SQL 与标准 SQL 在整体结构上的相似性。其三，BLEU 用于从 n-gram 匹配角度评估生成 SQL 与标准 SQL 的接近程度。本文还分别统计 overall、two_table 和 three_table 三个层面的结果，以比较模型在不同表数量场景下的生成表现。

需要注意的是，文本相似性并不完全等同于 SQL 语义正确性：两个形式不同的 SQL 可能具有相同执行结果，而文本相似的 SQL 也可能因连接条件或筛选条件错误而无法得到正确答案。因此，本文对 Text-to-SQL 结果的分析主要用于观察模型生成倾向和形式匹配程度，不对 SQL 的可执行性和执行结果正确性进行验证。SQL 执行评估、语义等价判断以及基于执行结果的错误分析可作为后续工作的改进方向。

## 2.6 本章小结

本章围绕 MMQA 多表多跳查询任务的相关工作进行了综述。首先介绍了单表问答和 Text-to-SQL 的发展过程，并说明本文并不以提出新的 Text-to-SQL 方法为主要目标，而是将其作为补充实验考察原始大语言模型的 SQL 生成能力。随后介绍了面向表格推理的大语言模型，分析了其在表格理解和跨表推理中的优势与局限。接着介绍了多表任务和 MMQA 评测基准，补充说明多表问答任务需要模型基于多张相关表直接推理并输出答案。最后介绍了多表检索、问题分解、Text-to-SQL 评估方法和常用评价指标。上述相关工作为第三章系统设计与第四章实验分析奠定了基础。
