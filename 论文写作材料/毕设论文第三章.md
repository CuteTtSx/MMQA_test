# 第三章 基于大模型的多表多跳查询系统设计与实现

传统的“检索-增强生成（RAG）”架构通常将检索与生成模块串联，但在处理复杂多表多跳任务时，这种强耦合的端到端设计会引发级联误差，掩盖大语言模型（LLMs）在单一维度的真实缺陷。为了精准探测与提升 LLMs 在多表环境下的能力边界，本文摒弃了常规的流水线系统，设计并实现了一套解耦的评估与增强框架。本章将详细阐述该解耦架构的设计理念，并深入解析多表检索（MTR）以及 Text-to-SQL 两大核心模块的具体工程实现细节。

## 3.1 系统总体架构

传统的表格问答系统多采用端到端（End-to-End）的流水线架构，即先由检索模块寻找相关表，再将检索结果（表）直接输入至 SQL 生成模块。然而，在复杂的多表多跳场景中，检索阶段引入的微小误差（如漏召回关键桥接表、误召回强干扰表）会不可逆地传递给下游的生成模块（级联误差），导致研究者无法准确判断最终的失败是源于“检索能力不足”还是“代码生成能力不足”。

为了精准定标大语言模型在各项核心任务上的能力边界，本文摒弃了容易掩盖问题的流水线设计，转而采用一种严格解耦的模块化架构（Decoupled Modular Architecture）。系统总体架构分为两条在评估阶段互相独立的链路：表检索链路与 SQL 生成链路。

**图 3.1 解耦的模块化系统架构图**

> - 左边框：多表检索模块（MTR）  
>   输入：全量数据库表池 + 复杂问题  
>   输出：Top-K 候选表 + 检索指标评估
> - 右边框：Text-to-SQL 生成模块  
>   输入：标准答案表头（Oracle Schema） + 复杂问题  
>   输出：生成 SQL + 语法和语义评估

具体工作模式如下：

多表检索链路 (MTR)：负责在庞大的全量全局表池（Global Table Pool）中，寻找解决复杂问题所需的表格子集。该模块包含问题分解器与迭代检索打分器，最终输出 Top-K 的表结构集合并进行 Precision、Recall 等检索指标的独立测算。 

Text-to-SQL 生成链路：为了屏蔽检索噪声，此链路的数据预处理阶段直接提取了包含绝对正确表结构的“标准表头（Ground Truth Schema）”。该标准 Schema 与原问题被组装为提示词输入大语言模型，重点考察模型在已知正确表结构的前提下，正确映射列名并编写复杂连表 SQL 语法的核心推理能力。

## 3.2 问题分解模块

在现实场景的复杂多跳查询中，用户的问题往往包含深层的逻辑嵌套（如交集、聚合计算等）。直接将此类长难句输入传统检索模型（如 BM25 或单表密集检索模型）容易导致“语义漂移”（Semantic Drift），使得检索系统抓取到错误的相关表。为此，本文引入了问题分解机制，**旨在将复杂的推理黑盒转化为可观测的离散步骤，从而为多表检索（MTR）模块的独立评估提供细粒度的语义锚点。**

### 3.2.1 基于少样本学习的分解器构建

本文利用大语言模型强大的上下文学习与指令遵循能力构建了问题分解器。为了确保分解过程符合关系型数据库的查询逻辑，并在工程实现上保持输出格式的稳定性，本文采用了少样本提示（Few-shot Prompting）策略。

系统提示词明确要求模型将复杂问题拆解为 2 至 5 个可独立回答的子问题，且子问题的顺序必须符合原始问题的内在逻辑。

### 3.2.2 鲁棒性控制与异常处理

在实际运行中，大模型的输出具有一定的随机性。为了保障**检索模块在批量自动化评估时的连续性与可靠性**，本模块在工程实现上引入了如下鲁棒性控制机制：

1. **长度截断与清洗**：解析大模型返回的 JSON 对象后，若生成的子问题链过长（超过5个），系统会执行强制截断，以防止过度发散引入检索噪声。
2. **退回机制与异常重试**：当大模型因网络波动或遇到极端复杂问题导致 JSON 解析失败时，系统设计了指数退避的重试机制。若达到最大重试次数依然失败，系统不会中断测试程序，而是触发“安全回退（Fallback）”，直接返回原始问题作为下一步的检索输入，从而保障批量评估程序的容错率。
3. **哈希缓存加速**：通过对原始问题计算 MD5 哈希值，系统实现了本地缓存机制，极大地降低了重复实验过程中的 API 调用开销与延迟。

## 3.3 多表迭代检索 (MTR) 算法设计

在将原始长难句拆解为子问题序列后，系统进入核心的多表迭代检索阶段。与传统单表检索仅依赖语义匹配不同，多表检索任务（MTR）面临着“语义漂移”与“孤岛表格”两大挑战。为此，本文以融合“语义相似度”与“表间结构关系”的双流打分思想为基础，并在工程实现上对问题-表打分、表间关系传播以及候选表更新策略进行了改造，引入最大连通性截断与残差平滑策略以优化迭代传播过程。

### 3.3.1 双流打分机制

本模块将数据库视为一个由表节点（Tables）和主外键边（Foreign Keys）构成的关系图。对于任意给定的子问题 $q_i$ 与候选表 $T_j$，检索器同时考虑问题与表之间的语义匹配程度，以及候选表与已检索表之间的结构关联程度。二者分别记为语义相似度 $\alpha$ 和拓扑连通度 $\beta$。
   
   **1.** **语义相似度计算 (**$\alpha$**)**
   
   语义得分主要衡量自然语言问题与表格模式（Schema）的字面及深层语义匹配度。原有的 MTR 算法采用基于大语言模型（如 TableLlama-7B）的生成式打分方法，该方法虽具备较强的理解能力，但在工业级海量表池中存在算力消耗大、推理延迟高的性能瓶颈。

   为了兼顾检索精度与实时性，本文对语义打分模块进行了**向量化**（Vectorization）改造。在具体实现中，本文首先将候选表$T_j$的表头元信息（包含表名及所有列名）格式化为结构化文本。随后，利用基于 Transformer 架构的密集嵌入模型（Dense Embedding Model），将分离的子问题文本  $q_i$   与表文本分别映射至统一的高维稠密向量空间。语义相似度$\alpha(q_i, T_j)$最终通过计算二者的高维特征向量内积（Dot Product）得出：
   
   $$\alpha(q_i, T_j) = \text{Embedding}(q_i) \cdot \text{Embedding}(T_j)$$
   
   该方法将计算复杂度由昂贵的自回归生成降维为极速的矩阵乘法，使得系统具备了在毫秒级内完成大规模数据库扫描的工程可行性。
   
   **2. 拓扑连通度计算 (**$\beta$**)**
   
   大语言模型或向量模型在处理形如“ID”、“Name”等通用列名时极易产生幻觉，赋予无关表格高语义得分。为此，本文引入了基于底层数据库物理结构的拓扑惩罚因子$\beta$ 。设上一轮检索保留的锚点表集合为$C_{t-1}$，对于当前评估的候选表$T_j$，系统严格校验其与锚点表   $T_k \in C_{t-1}$之间的主外键（PK-FK）依赖关系。
   
   若 $T_k$与 $T_j$存在明确的主外键映射或共享外键（如桥接表关系），则判定为强连通赋值得分 $\beta(T_k, T_j) = 1.0$；若两者在物理层面上相互独立（即“孤岛表”），则施加严厉惩罚，仅保留基础底分$\beta(T_k, T_j) = 0.1$。该机制通过硬性的结构逻辑，有效过滤了高语义但结构无关的干扰表。
   

### 3.3.2 迭代传播与残差平滑策略

原有的图注意力传播算法在多轮迭代中极易因过度累加导致中心表（连通边极多的基础表）分数异常膨胀，产生“雪球效应”。为解决此问题，本文在 MTR 迭代流水线中进行了两项关键的算法改良：

**1. 最大连通性截断 (Max-Connectivity)**

在第t轮迭代中，对于候选表T_j，算法不再累加其与所有锚点表的连通得分，而是仅取**最强的一条连接路径**。结合子问题集Q，候选表的传播得分$S_{prop}$ 计算如下：

$$S_{prop}(T_j)=\frac{1}{|Q|}\sum_{q_i \in Q}\left(\alpha(q_i, T_j)\times\max_{T_k \in C_{t-1}}\beta(T_k, T_j)\right)$$

该策略确保了算法始终沿着最短且最紧密的物理路径进行表格探索。

**2. 动量残差保留 (Momentum Smoothing)**

在多轮网络传播中，初始轮次捕获的高纯度语义信息极易被后续复杂的图拓扑特征稀释。为此，本文在每轮分数更新时引入了残差连接思想。最终得分$S_{new}$由当前轮的传播得分$S_{prop}$与上一轮的历史得分$S_{old}$加权融合而成：

 $$S_{new}(T_j)=\lambda\cdot S_{prop}(T_j)+(1-\lambda)\cdot S_{old}(T_j)$$

在本文实验中，设$\lambda = 0.8$。该平滑因子使算法在向外探索新表的同时，兼顾并锁定了初始锚点表的语义信誉，极大地提升了检索排名的稳定性。

## 3.4 Text-to-SQL 生成模块

在多表多跳查询系统中，Text-to-SQL 模块的核心任务是将用户的自然语言转换为可在数据库中执行的结构化查询语言。为了严格剥离检索阶段可能带来的级联误差，精准评估并提升大语言模型跨表逻辑推理与代码生成能力，本研究在 Text-to-SQL 的微调与测试阶段采用了“标准视角（Oracle）”的解耦设计。

### 3.4.1 基于标准表头的微调数据构建

大模型处理长文本时存在典型的“迷失在中间”（Lost in the Middle）现象，且有限的显存（VRAM）难以承载包含成千上万行具体记录的原始数据表。因此，在构建微调数据集（Dataset Construction）时，本研究采用了严格的数据降噪策略。 

如数据预处理脚本 prepare_finetuning_data.py 的逻辑所示，系统在内存中深度拷贝原始数据后，强制剔除所有庞大的表内容字段（table_content），仅保留与 SQL 生成直接相关的结构化 Schema 信息（即表名与列名集合）。通过这种极简的 Prompt 拼接方式（表 3.2 所示），不仅将输入 Token 数量压缩了数个数量级，还有效消除了底层脏数据对模型注意力机制的干扰。

### 3.4.2 基于 LoRA 的低秩微调实现

在针对庞大的基座模型参数量（如 Qwen2.5-1.5B-Instruct），全参数微调会导致严重的显存溢出（OOM）问题。为此，本文采用了高效的 LoRA（Low-Rank Adaptation）微调技术。 

在模型训练配置（finetune_qwen.py）中，系统采用了 BF16（Brain Float 16）混合精度格式以确保梯度更新的数值稳定性，避免半精度浮点（FP16）带来的溢出风险。通过 PEFT（Parameter-Efficient Fine-Tuning）库，微调过程冻结了原模型的大部分权重，仅在注意力机制的核心模块（q_proj, k_proj, v_proj, o_proj）旁注入低秩外挂矩阵。此外，结合极小的单设备批次大小（per_device_train_batch_size=1）与梯度累加（gradient_accumulation_steps）策略，本模块在有限显存环境（消费级显卡 RTX 3060 6GB）下实现了可训练的跨表 SQL 生成模型，并增强了模型对 INNER JOIN 等复杂 SQL 结构的生成能力。
